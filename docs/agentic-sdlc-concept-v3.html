1. Business analysis agent

Agent stage

↕ Reads from / writes to the Shared state store

→ Command center: Feature layer

Prerequisites

  • Raw requirement document available
  • Access to relevant existing system context/docs, if any

Definition of done

  • Tickets written to state store, ADO work-item schema
  • Dependency DAG persisted, each edge with reasoning
  • Feature groupings proposed alongside the ticket set
  • Ambiguities / open questions list produced separately
  • Human approval recorded on both tickets and DAG

2. Planning agent

Agent stage

↕ Reads from / writes to the Shared state store

→ Structured logging

Prerequisites

  • Ticket status = approved
  • All DAG-predecessor tickets already merged

Definition of done

  • Implementation plan written to store
  • Assumptions & trade-offs document written, versioned to this plan
  • Ticket status advances to spec_authoring

3. Spec author

Agent stage

↕ Reads from / writes to the Shared state store

→ Structured logging

Turns the approved plan into the detailed technical spec Implementation Agents actually build against — interface and API contracts, data models, and edge cases. Sits immediately before Plan Critique so the spec is reviewed as part of the same gate as the plan, not left unreviewed downstream.

Prerequisites

  • Plan + assumptions document present in store

Definition of done

  • Technical spec written to the store, versioned to the plan
  • Interface contracts, data models, and edge cases made explicit
  • Ticket status advances to plan_critique

4. Plan critique

Quality gate · loops back to Spec author on any blocker

↕ Reads from / writes to the Shared state store

→ Critic integrity safeguards→ Prometheus + Grafana→ Per-stage eval metrics→ Human decision queue

Now critiques the plan, its assumptions, and the technical spec together as one package, against all four pillars.

Prerequisites

  • Plan, assumptions document, and spec all present in store

Definition of done

  • Critique entries persisted: severity (blocker/major/nitpick) × pillar (perf, security, scale, maintainability)
  • Zero open blockers — auto-loops to Spec author if any exist
  • Majors resolved or explicitly human-overridden via the Human decision queue
  • Retries are bounded — exceeding the limit escalates to the Human decision queue instead of looping again
  • Ticket status advances to plan_approved

5. Implementation agents

Agent stage

↕ Reads from / writes to the Shared state store

→ Structured logging

Prerequisites

  • Ticket status = plan_approved
  • Isolated branch created

Definition of done

  • Code committed to isolated branch, linked to ticket
  • Ticket status advances to code_critique

6. Code critique

Quality gate · loops back to Implementation on any blocker

↕ Reads from / writes to the Shared state store

→ Critic integrity safeguards→ Prometheus + Grafana→ Per-stage eval metrics→ Human decision queue

Prerequisites

  • Code artifact present and linked to ticket

Definition of done

  • Same four-pillar critique, applied to actual code
  • Schema/migration changes auto-flagged major minimum
  • Zero open blockers — auto-loops to implementation if any exist
  • Retries are bounded — exceeding the limit escalates to the Human decision queue instead of looping again
  • Ticket status advances to qa_strategy

7. QA test strategy

Agent stage

↕ Reads from / writes to the Shared state store

→ Offline eval set

Plans what gets tested and why — risk-based prioritization, edge cases drawn from the spec and plan, and which layers (unit, integration, UI) matter most for this specific change. Test & Verify stays pure execution; this stage does the thinking beforehand, the same split already used between Planning and Implementation.

Prerequisites

  • Code critique passed, zero open blockers
  • Spec and plan available for risk analysis

Definition of done

  • Test strategy document written to the store: scope, priorities, risk areas
  • Ticket status advances to testing

8. Test & verify

Agent stage

↕ Reads from / writes to the Shared state store

→ Offline eval set→ Loki

Prerequisites

  • Test strategy document present in store

Definition of done

  • Unit + integration tests run per the test strategy, results stored
  • Playwright run executed — screenshots + ffmpeg video linked
  • All required tests passing, or a documented known-fail with human acknowledgment
  • Ticket status advances to pr_ready

9. PR packaging, review & human merge

Human-owned · includes an automated PR review sub-step

↕ Reads from / writes to the Shared state store

→ Human feedback signal→ Status rollup

Before a human ever sees the PR, two checks run automatically. Deterministic hygiene checks, enforced by the orchestrator directly, confirm the ticket is linked, the critique trail and test evidence are attached, and no unrelated files are touched. A lighter review step then checks whether the PR description actually matches the diff, flagging any mismatch as an annotation for the human reviewer rather than as a blocker — this is not a new gate, and it carries no severity tiers or retry bound of its own.

Prerequisites

  • Testing complete, all evidence artifacts linked

Definition of done

  • PR opened in ADO — diff, critique trail summary, test evidence attached
  • Hygiene checks passed; description-accuracy review completed, with any mismatch flagged for the reviewer
  • Human review completed
  • Merged, or sent back with recorded reason

Orchestrator

The control layer that keeps tickets moving — not an eighth agent

What it does

  • Dependency-aware scheduling: dispatches a ticket the moment its DAG predecessors are merged and its status is ready for the next stage
  • Routes each ticket to the correct agent based on its current status
  • Reads gate findings and applies the branch logic: blocker routes back, no blocker advances
  • Tracks retry_count per ticket per gate and enforces the bound, routing to escalation once exceeded
  • Pauses a ticket entirely at a human checkpoint and resumes only once a human_decision record appears

Why it has no memory of its own

  • Every decision it makes is read fresh from the shared state store, never held between invocations
  • This is what lets it restart, crash, or run as multiple parallel workers without losing track of any ticket
  • It is the deterministic control layer the database-mediated design principle was built to support — not a model call, just scheduling and routing logic

Shared state store

The backbone underneath all seven pipeline stages

What it is

  • Not a pipeline stage — the persistence layer every stage depends on
  • Holds tickets, the dependency DAG, plans, assumptions documents, critiques, code artifacts, and test results

Why it works this way

  • No agent ever passes context directly to another agent
  • Every stage reads its input from, and writes its output to, this store exclusively
  • This is what makes the critic-integrity safeguards possible (Appendix), and what makes the whole pipeline fully auditable after the fact

Structured logging

Appendix · Observability

What

  • Every agent invocation logged as structured JSON
  • Ticket ID, agent, stage, input hash, token count, latency, outcome

Why

  • Cheapest, most immediate signal — exists before anything else in the stack

Prometheus + Grafana

Appendix · Observability

Tracks

  • Token consumption per stage/ticket over time
  • Agent latency p50/p95/p99
  • Retry/loop counts per gate
  • Blocker/major/nitpick rate per pillar

Why

  • Answers the cost question directly
  • Retry spikes flag agent or critic degradation
  • Severity trend is a leading health indicator

Loki

Appendix · Observability

What

  • Correlates a Grafana metric spike back to the exact log lines that caused it
  • Can also hold each agent's prompt and response, keyed by ticket ID

Why

  • No separate log pipeline needed — pairs directly with structured logging
  • The lowest-cost way to reconstruct exactly what an agent was given
  • Prompts contain code and plans, so access to these logs must be restricted

Tempo

Appendix · Observability

What

  • The distributed-tracing backend that sits alongside Loki and Grafana
  • With OpenTelemetry instrumentation, each ticket's journey is a trace, and each agent call, gate decision, and retry is a span within it

Why

  • Answers what metrics cannot: within one ticket's path across stages and retry loops, where did the time go?
  • Traces link to Loki logs and Grafana metrics through the ticket ID, so an operator moves from a slow-ticket alert to its trace to its log lines in one place

LLM trace viewer (optional)

Appendix · Observability · added conditionally, not by default

Metrics, logs, and traces cover cost, health, and timing, and the state store already holds every plan, finding, and decision. What they do not show is an agent's exact prompt, intermediate steps, and tool calls, or side-by-side prompt experiments. Langfuse or LangSmith fills that gap if it earns its place.

Add it when

  • Debugging a flagged ticket keeps requiring an agent's exact reasoning, and logs and traces cannot explain it
  • Prompt or model changes are run as experiments that need side-by-side comparison

Three questions decide the choice

  • Can traces containing code and plans leave the network? If not, only self-hosted options remain
  • Will the orchestration layer stay on its current framework? If it may change, prefer the framework-agnostic option
  • Who will operate the infrastructure? Self-hosting trades licence cost for operational effort

Offline eval set

Appendix · Evals

Built from

  • Fixed set of past tickets with known-good plans/code as ground truth

Run

  • On every model/prompt change, and on a regular schedule
  • Scores plan match, critique catch-rate, code pass-rate
  • Functions as the regression suite for the agentic system itself

Per-stage eval metrics

Appendix · Evals

Why not end-to-end only

  • "Ticket eventually merged" is too coarse — hides costly retry loops behind an apparent success

Track per gate

  • Blocker rate
  • False-positive rate (human overrode the blocker)
  • Retry count before pass

Human feedback as a labeled signal

Appendix · Evals

Capture

  • Every override, rejection, or send-back — written structurally to the state store, not left in a Teams message

Review

  • Periodic batch review: are critics too lenient on security, too strict on style, etc.
  • This is how the system improves over time rather than staying static

Cost-quality tradeoff tracking

Appendix · Evals

Track

  • Token spend per ticket against outcome quality

Enables

  • Tiered-matching-style optimization — short-circuiting expensive calls for high-confidence cases, informed by real per-ticket data

Feature layer

Command Center · schema addition

New unit, above ticket

  • Ask — one raw requirement doc (an epic/initiative)
  • Feature — cluster of related tickets within an ask
  • Ticket — the existing atomic unit

How it's populated

  • Business analysis agent proposes groupings alongside the DAG — no new agent needed
  • Add feature_id to the ticket schema, plus a features table

Status rollup

Command Center · computed live, not stored

Feature status

  • Complete only when every child ticket = merged
  • In-progress if any ticket is active
  • Blocked if any ticket stuck with nothing else moving

Ask status

  • Same rollup logic one level up
  • Never stored — always derived, so it can't go stale against reality

Stuck detection

Command Center · precise definition

A ticket is stuck if

  • Explicitly in blocked or needs_human state
  • Exceeded its bounded retry limit at a gate
  • Stage time exceeds the learned p95 — comes free from Prometheus

Rolls up the same way

  • Feature-level: any child ticket stuck, nothing else moving
  • Ask-level: same, one level up

Drill-down views

Command Center · read-only queries

Ask view

  • List of asks, % complete, feature counts by status
  • Oldest stuck item, total token spend

Feature & ticket views

  • Feature: child tickets by status, dependency %, what's stuck and why
  • Ticket: state position, critique history, retry vs. bound, stage time vs. p95, evidence links

Human decision queue

Command Center · where a person actually acts

Review required (a gate found a major issue)

  • Ticket pauses and appears in this queue, separate from the status dashboard
  • Shows the plan or code, its assumptions, and the specific finding with its cited evidence, side by side
  • Approve — accepts the finding as-is; ticket proceeds to the next stage
  • Reject — sends back to the generating agent with the finding attached as required context; counts against the retry bound
  • Edit — a person modifies the artifact directly; submitted straight to re-critique

Escalated (retry bound exhausted)

  • Shown separately and with higher priority than a routine review, since agents demonstrably failed to converge
  • Displays every attempt — each version and its findings — so a person can see whether the agent was converging or repeating the same mistake
  • Resume with guidance — a person supplies corrective direction; retry count resets and the ticket re-enters the pipeline carrying that guidance
  • Force-advance — accepts the current state despite the standing issue; requires a written justification
  • Kill or re-scope — cancels the ticket, or sends it back to Business Analysis for re-decomposition

Critic integrity safeguards

Appendix · applies to both quality gates

Structural

  • Critic never sees the generator's reasoning — only the finished artifact in the store
  • Every finding requires a specific reference plus concrete reasoning — vague findings are rejected and force a retry
  • Prompt requires active justification for a clean pass, not silent default approval

Monitored over time

  • Offline eval set seeded with deliberately flawed plans/code; catch-rate drop is the drift signal
  • False negatives tracked explicitly, not just override rate
  • Highest-stakes tickets get a second independent critique pass; disagreement routes to a human
